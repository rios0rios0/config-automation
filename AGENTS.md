# AGENTS.md

This file provides guidance to AI coding agents (Claude Code, Codex, Cursor, GitHub Copilot) when working with code in this repository.

## What This Repository Is

This repo houses **scheduled, cross-repo maintenance workflows** that run from a central location and act on every repository of every owner listed in `HARDEN_OWNER` (currently `rios0rios0`, `medhub-life`, and `prefy`), plus the Go CLI they drive.

**One job per owner is the workflow baseline.** Because a fine-grained PAT is bound to a single resource owner, every scheduled workflow that talks to GitHub fans out with `strategy.matrix.owner` (`fail-fast: false`) and gives each leg its own owner and its own token. `sonar-analysis-policy.yaml` is the one exception, and deliberately so: it talks to SonarQube Cloud, where only `rios0rios0` has an organization at all. `config-and-docs-refresh.yaml` additionally enumerates each owner separately and keeps going past an unreachable one, then fails the run in its terminal `verify` job — so a skipped owner is loud instead of silently shrinking the fleet.

**Multi-owner is the CLI's baseline, not a special case.** `HARDEN_OWNER` is a comma-separated list; every phase loops over it. Two consequences are load-bearing: a repository is identified by its `owner/name` slug (`entities.Repository.QualifiedName()`) because bare names collide across owners — `medhub-life/frontend` and `prefy/frontend` both exist today — and the mutating phases receive per-owner command inputs, which is why `executeAuditPerOwner` keeps the audits grouped instead of returning one flat slice. Anything that maps, keys, or reports repositories must use the qualified name; keying on the bare name silently attributes one owner's drift to another's repo.

1. **`.github/workflows/repo-compliance-audit.yaml`** — daily (06:00 UTC) audit that runs `go run ./cmd/harden-repos --phase 1 --fail-on-noncompliant` against every repo of every configured owner. Fails if any repo drifts from the compliance policy. Uploads `/tmp/gh_hardening_audit_before.json` as an artifact.

2. **`.github/workflows/config-and-docs-refresh.yaml`** — weekly (Mondays 07:00 UTC) **batched-matrix** workflow that runs the `refresh-docs` CLI (`cmd/refresh-docs`), named for the broader scope (configuration + documentation) so future targets can be added without renaming. The `discover` job runs `refresh-docs discover`, which lists every owner in `.config-automation.yaml` with that owner's own token and chunks each owner's repos into batches of `batch_size` (default 10), so every leg carries one owner and the name of its secret (`credential`); a single-repo `workflow_dispatch` (`repo`) refuses a fork, an archived or a disabled repo. Each `refresh` leg (`max_parallel: 2` by default) runs `scripts/install-refresh-tools.sh`, then `refresh-docs run` over its batch with `GH_TOKEN` from `secrets[matrix.batch.credential]`. The same CLI runs on Azure DevOps through `azure-devops/jobs/refresh-config-and-docs.yaml`. **The config-and-docs refresh** below holds its invariants.

3. **`.github/workflows/sonar-analysis-policy.yaml`** — daily (06:30 UTC) job that runs `go run ./cmd/harden-repos --sonar-policy` against every project of the `rios0rios0` SonarQube Cloud organization. It is the one scheduled workflow with **no owner matrix**: `medhub-life` and `prefy` have no SonarQube Cloud organization, so a leg for them would only ever return `No organization for key`. Per project it adds the missing `sonar.issue.ignore.multicriteria` pairs from `entities.DesiredSonarIssueExclusions()`, accepts the still-open issues of those rules (`api/issues/bulk_change`, `do_transition=accept`), and marks their `TO_REVIEW` hotspots `REVIEWED`/`SAFE` (`api/hotspots/change_status`). `workflow_dispatch` exposes `project` and `dry_run`. **The setting has to be written per project, not committed to the repo:** every project runs SonarQube Cloud automatic analysis, which reads only `sonar.sources`, `sonar.exclusions`, `sonar.inclusions`, `sonar.tests`, `sonar.test.exclusions`, `sonar.test.inclusions`, `sonar.sourceEncoding`, `sonar.cpd.exclusions`, `sonar.python.version` and `sonar.cfamily.reportingCppStandardOverride` from `.sonarcloud.properties` — there is no issue-exclusion key among them, so a `.sonarcloud.properties` entry would be silently ignored. **The exclusion and the triage are two halves of one fix and neither replaces the other:** the exclusion only takes effect on the next analysis (under automatic analysis, the next push), so alone it leaves every gate red in the meantime; the triage clears what is already recorded and makes the gate recompute now, but says nothing about the next occurrence. Do not "simplify" the command down to either half.

4. **`.github/workflows/release-reconcile.yaml`** — weekly (Mondays 08:00 UTC) safety net for the "bumped but never released" failure mode: a bump PR merges but that repo's `main` run fails the pipelines quality gate, so `delivery-release` never runs and no tag/release is cut even though `CHANGELOG.md` already carries the version. The job enumerates repos via `go run ./cmd/harden-repos --list-json`, clones `pipelines` for the single-sourced detector `global/scripts/shared/reconcile-releases.sh`, then runs `scripts/reconcile-repos.sh` — which blobless-clones each repo, diffs its released changelog versions against its tags, and (re-)pushes a missing tag at its bump commit. The tag push re-triggers the `pipelines` tag-push delivery path (the gate jobs skip on tags), which re-cuts the release. Pushes use that owner's PAT — a `GITHUB_TOKEN`-pushed tag would not start the delivery workflow. `workflow_dispatch` exposes `repo` (single-repo), `dry_run` (detect + report only), and `fail_on_gap` (exit non-zero on an unrecoverable gap) inputs; results are written to `$GITHUB_STEP_SUMMARY`. Detection is single-sourced in `pipelines` (and tested there), so this repo owns only the org-wide orchestration. **Only a version above the repository's highest SemVer tag is pushed.** Every tag push deploys, so a gap at or below that tag is a bump a later release superseded, and pushing it would roll the deployment back: until 2026-11-03 the job re-pushed `medhub-life`'s superseded bumps (frontend `0.4.0` after `0.4.1`, backend `2.1.0`/`2.1.1` after `2.1.2`) every Monday, so `medhub-life`'s leg was paused (#121) until this floor existed (#122). Such a gap is logged as `skipped: <version> is below the highest tag <tag>` (or `equals`) and does not count toward `fail_on_gap`, with or without a bump commit. The order is SemVer precedence over the tags that parse as SemVer (an optional `v`, pre-release below its release, build metadata ignored; `v8`, `v2.5`, `latest` do not count), computed in jq in `VERSION_ORDER_JQ`; the detector's fork variant `X.Y.Z-N` is read both as a SemVer pre-release and as the fork's `X.Y.Z.N`, and a gap must be above the highest tag under both readings. A repo whose tags cannot all be fetched is reported and not scanned, since its floor would be incomplete. git authenticates through a credential helper that answers from `GH_TOKEN`, set with `GIT_CONFIG_*` in the environment so the detector's on-demand blob fetches authenticate too; the token is in no clone URL or command line, which is what lets the script print git's own output for a failed clone, tag fetch or tag push (indented under the line it explains) rather than discarding it. The suite in `test/scripts/reconcile_repos_test.go` runs the script against local bare repositories with a detector double.

5. **`cmd/harden-repos/`** — the Go CLI that implements the compliance policy. Understanding its architecture is required before editing.

## `AGENTS.md` layout

`AGENTS.md` is the instruction file in every repository the refresh touches; each
`CLAUDE.md` beside one contains only `@AGENTS.md`, the import Claude Code documents
for sharing one file with other agents. `refresh-docs layout` (`cmd/refresh-docs`) enforces that
deterministically, before the audit, for every directory outside `.claude/` and the
excluded dependency/build directories:

- a `CLAUDE.md` with no `AGENTS.md` is renamed with `git mv` and committed alone
  (`chore(refresh): renamed ...`), so `git log --follow AGENTS.md` keeps its history,
  then recreated as the import, and its legacy banner is replaced;
- a `CLAUDE.md` beside an `AGENTS.md` is appended to it under
  `## Migrated from CLAUDE.md`, unless `AGENTS.md` already holds that text line
  for line (the refresh integrates it), then becomes the import;
- an `AGENTS.md` without a `CLAUDE.md` gets the import, and a symlink between the two
  becomes the import file (Edit cannot write through a symlink);
- a pair holding any other symlink, an ignored path, or a non-UTF-8 file is
  reported, and neither of its files is changed;
- with `claude` off, legacy text still moves into `AGENTS.md` and every paired
  `CLAUDE.md` is removed instead of becoming the import.

The rename commit moves `HEAD`, so drift is measured against it and the branch
carries two commits. A second pass after the refresh adds the import for an
`AGENTS.md` the refresh created. The report becomes the prompt's
`## Guidance layout for this repository` section, which also tells Claude to record
the move in the changelog.

## The config-and-docs refresh

One implementation serves both platforms. Providers are adapters: `entities.Provider` maps `github` and `azuredevops` to their clone URL, PR URL, git credential host and user, and instruction-file defaults; GitHub discovery uses this repo's go-github adapter, Azure DevOps discovery and both providers' pull requests use [gitforge](https://github.com/rios0rios0/gitforge). CI dialects are presenters in `cmd/refresh-docs/presenters.go` (GitHub Actions, Azure Pipelines, plain). An organization's data lives only in its consumer's configuration file, never in this repository.

- **Discovery** (`DiscoverRefreshTargetsCommand`) lists each configured organization with its own token and batches within it. An organization it cannot list, or whose token is empty, is recorded and the rest are still batched; `failed_organizations`, an output in both dialects, lets the `verify` job of the workflow and of the Azure Pipelines template turn the run red, and `discover` exits non-zero only when no organization could be listed. A listing is complete or an error, never partial. GitHub goes through `commands.FindOwnedRepositories` (the owner/authenticated-login/`OwnerKind` paths `--list-json` uses), never gitforge's GitHub discovery, which falls back to public repositories when `/user` fails; Azure DevOps goes through gitforge's strict org-level `ListOrganizationRepositories`. Forks, archived, disabled and empty repos and `refresh.exclude` entries are left out, and `--repo` naming one is refused. GitHub reports a default branch even for an empty repository, so `run` also records a clone whose default branch has no commit as `no_drift` instead of failing it.
- **Per repository, in order** (`RefreshRepositoriesCommand`): clone, checkout, layout, scope, changelog convention, audit and refresh, layout again, chlog guard and fragment provenance, drift, secret-shape guard, branch/commit/force-push, find or open the PR. **Every failure is recorded under its reason and never aborts the batch**; a panic is recovered as `internal:`, and the agent's stream is closed however its phases end, so a CI's stop-commands never swallow the rest of the leg. The reasons are `clone checkout layout scope claude claude-quota changelog-guard fragment drift secret-shape stage branch commit push pr-list pr-create internal`.
- **No token reaches the agent or the clone.** `GitClonesRepository` clones a credential-free URL and hands git the token only through `-c credential.helper=` (clearing the machine's helpers) plus a helper that answers from variables set on that one git process, for the provider's host alone: never in a URL, `argv`, or the clone's `.git/config`, and a redirect cannot carry it elsewhere. `ClaudeCodeAgentRepository` withholds every hosting token variable (`hostingTokenVariables()`, every `${NAME}` a configured provider token reads, and `--token-env`), denies reads under `/proc` (`--disallowedTools 'Read(//proc/**)'`, since its parents' environments hold the token), detaches stdin, disables settings, hooks and MCP servers (`--setting-sources '' --strict-mcp-config`), and runs `--permission-mode dontAsk`; `CLAUDE_CODE_OAUTH_TOKEN` is the one secret left. `run` refuses to start without its token (empty, or a `$(NAME)` Azure Pipelines left literal) and never falls back to another variable, such as a pipeline's own project-scoped token.
- **Every file grant is an `Edit(...)` rule, never `Write(...)`:** the CLI matches file permissions on `Edit` rules alone (an `Edit` grant covers `Write` too); a `Write(...)` rule is inert and only warns. The grants are the scope manifest's; the one other grant is the chlog command.
- **Failure classification** (`entities.ClassifyAgentFailure`): `monthly (usage|spend) limit`, `hit your (weekly|5-hour) limit` or the `usage_limit_reached` code is account-wide, so it records `claude-quota:` and the rest of the batch is `quota_skipped`; a safeguard refusal (anchored on `flagged this message for a cybersecurity topic`, the phrase both its wordings share, plus `safeguards flagged`, `cyber-use-case`, `real-time-cyber-safeguards` and `cyber verification program`) is deterministic for that one repo, so it is `safeguard_skipped` plus a warning annotation and **not** a failure (as a failure it kept a leg red over a repo nothing could fix: do not fold it back into `failed`, nor drop the annotation); anything else is `claude:`. On Azure Pipelines a batch whose only trouble is a safeguard skip ends `SucceededWithIssues`.
- **The changelog target is chosen per repo and enforced by the grant, not the prompt:** `chlog` when `.chlog.yaml`, `.chlog.yml` or `.changes/unreleased/` exists (the `pipelines` basic-checks predicate, which mirrors AutoBump's `DetectChlog`) grants `Bash(chlog new:*)`; `changelog` (only `CHANGELOG.md`) grants `Edit(/CHANGELOG.md)`; `none` grants nothing. A symlink at a chlog path counts as chlog, as the predicate's `-f` and `-d` follow one. In chlog mode the host restores any `CHANGELOG.md` or existing-fragment edit and rejects (`fragment:`) a new fragment missing `kind`/`body`/`time`, whose 19-digit nanosecond filename and `time` disagree by more than two seconds (a hand-typed fragment), or whose `time` is in the future. A grant that allowed hand edits is how the 2026-08-31 run rewrote 46 generated changelogs. The changelog is staged with the drift but is not part of the drift gate, so a changelog-only edit opens no PR.
- **Drift** is the manifest paths after intent-to-add, measured with `git diff HEAD -w --quiet`; an exit above 1 is an error, never drift. The branch is published on drift **or** when `HEAD` is ahead of the remote default branch (the layout's rename commit, a host removal).
- **The secret-shape guard reads the added lines** of the drift and the staged changelog entry and refuses the repo (`secret-shape:`) on the hyphenated Slack bot-token prefix, a private-key banner, a completed GitHub or AWS prefix, a fine-grained GitHub token, an Anthropic token, an Azure DevOps token in its 84-character format, or a JWT; an unreadable diff is a refusal too. The diff is taken with `--text --no-ext-diff --no-textconv`, so a repository's `.gitattributes` cannot turn its lines into "Binary files differ" or route them through a driver. Gitleaks' GitLab-customised pass fires on some prefixes alone and the scan on `main` walks the whole history, so only a `.gitleaksignore` fingerprint, which no grant can write, clears a finding: the 2026-08-26 run planted one in ~40 repositories. Added lines only, so older text never fails a run that did not write it. The prompt's approved secret-hygiene wording and this guard move together.
- **Repository-controlled text never acts as a CI command:** the GitHub Actions presenter wraps it in `::stop-commands::` with a random resume token, and the Azure Pipelines presenter defuses every `##vso[`, whatever its case, in each line, the streamed agent output included.
- **Instruction files** (`entities.InstructionFiles`) are `agents`, `claude` and `copilot`, defaulted per provider (Copilot off on Azure DevOps); a flag beats `refresh.instruction_files`, which beats the default. With `agents` off no `AGENTS.md` is offered for creation at all, not even the one an import points at. The layout pass removes a disabled kind before the audit and leaves it an unstaged deletion; the manifest lists it under `removed` (staged and drift-checked, never granted), and the prompt template `internal/domain/entities/prompts/refresh_config_and_docs.md` (`text/template`) drops the matching rules.
- **Pins:** `scripts/install-refresh-tools.sh` is the one place the Claude CLI range and the chlog version and checksum live, for both CIs. The Azure Pipelines template takes the consumer's pinned commit as `expectedSha` and re-checks it after every checkout; its checkouts have explicit `path:` values because both repositories are usually named `config-automation`.
- Branch `chore/config-and-docs-refresh` is force-pushed and one PR is kept open per repo; a failed lookup opens none (`pr-list:`), so a transient error never doubles a PR. Each leg prints `processed / no_drift / prs_created / prs_updated / quota_skipped / safeguard_skipped / failed` and exits non-zero only on `failed`.

### Prompt audit and refresh model

`refresh-docs run` runs the bundled `/checkup prompt-audit .` skill (an
alias of `/doctor prompt-audit`) in print mode before editing. Its audit sees
repository instruction files, `AGENTS.md` first, including nested guidance, rules,
skills, agents, and commands, with only `Read,Grep,Glob` available and user/project
settings and MCP servers disabled. It emits the report and proposed diff to the job
log; a failed, empty, or unsuccessful JSON result stops that repository before
editing and enters the existing batch failure handler. Git provenance is unavailable
to the audit, so ambiguous conflicts remain findings.

The second invocation verifies audit findings and factual documentation drift in
the exact files listed by the scope manifest. It covers root/nested `AGENTS.md`,
`.claude/CLAUDE.md`, `.claude/rules/`, Markdown skills and their references under
`.claude/skills/` and `.github/skills/`, agent definitions under `.claude/agents/`
and `.github/agents/`, `.claude/commands/`, Copilot instructions/prompts, root
README, and CONTRIBUTING at the root, `.github/`, `.azuredevops/`, or `docs/`.
Existing files only, plus the optional creation targets the instruction-file settings allow. It holds `AGENTS.md` to Claude Code's
under-200-lines guidance. Preserve frontmatter, permissions, model pins, generated
sections, and deliberate directory overrides. Other findings stay in the log for
human review. Both calls use `CLAUDE_MODEL` (default `claude-opus-5-5`) and
`CLAUDE_EFFORT` (default `high`; Opus 5.5 otherwise runs at `medium`), detach
stdin, skip the target repository's settings, hooks, and MCP servers, run with
`--permission-mode dontAsk`, and have their own `MAX_TURNS` limit. The refresh lists
its tools explicitly because the default Linux tool set lacks `Grep` and `Glob`.

## The `harden-repos` CLI

Clean Architecture split:

- **`internal/domain/entities/`** — framework-agnostic data types: `Repository`, `SecuritySettings`, `BranchProtection`, `Ruleset`, `AuditResult`. `compliance_policy.go` exposes the policy every other package references: `DesiredRepoSettings()` and `DesiredWikiAllowlist()` are functions (returning fresh values so the policy stays immutable at call sites); `DesiredReviewCount`, `DesiredForkActionsEnabled`, `DesiredRulesetName`, `DesiredDefaultBranch`, and `RepositoryAdminActorType`/`ID` remain constants. `AuditResult.ComputeIssues()` is the single source of truth for policy compliance and encodes every carve-out (forks skip Dependabot + secret scanning and must instead keep GitHub Actions disabled — `DesiredForkActionsEnabled`, reported as `actions_enabled`, never checked on a non-fork — private repos skip secret scanning + branch protection + rulesets, `DesiredWikiAllowlist()` repos keep `has_wiki=true`, `AllowAutoMerge=true` is skipped on private repos because GitHub Free silently ignores the PATCH).
- **`internal/domain/repositories/`** — four ports: `Repository`, `SecuritySettingsRepository`, `BranchProtectionsRepository`, `SonarProjectsRepository`. Each is a small interface with the methods the commands actually need. The domain layer never imports `github.com/google/go-github`. `BranchProtectionsRepository.FindRulesetByName` returns the sentinel `repositories.ErrRulesetNotFound` when no ruleset is configured; callers treat it as "no ruleset" rather than propagating it as an error.
- **`internal/domain/commands/`** — one command per phase plus `--list-json`: `AuditRepositoriesCommand`, `ApplyRepositorySettingsCommand`, `ApplySecuritySettingsCommand`, `ApplyBranchProtectionCommand`, `ListTargetRepositoriesCommand`, `ReportComplianceChangesCommand`. Every command exposes a listeners struct (`OnSuccess`, `OnError`, `OnChange`, etc.) so the CLI layer (which plays the controller role) maps outcomes to stdout and exit codes.
- **`internal/infrastructure/repositories/`** — `GoGithub…Repository` adapters that implement the ports by calling `github.com/google/go-github/v93`. Each also handles the HTTP-status idioms the Python original encoded: 204 vs 404 for vulnerability alerts, 403/404 for branch protection unavailability, rate limits, etc.
- **`cmd/harden-repos/main.go`** — parses flags, dispatches to commands with listeners that print via Logrus and set exit codes.

Key invariants to preserve when editing:

- `Repository.FindAllByOwner` branches on whether the owner equals the authenticated login (then `/user/repos` retains private visibility) and on `OwnerKind` (`User` vs `Organization`). Keep all three paths in sync.
- `SecuritySettingsRepository.FindByRepositoryName` returns `DependabotAlerts *bool` — nil means "unknown" (API failure), pointer-to-false means "disabled". `AuditResult.ComputeIssues` distinguishes the two; don't collapse them. `ActionsEnabled *bool` carries the same tri-state for the repository-level GitHub Actions switch, read from `GET /repos/{owner}/{repo}/actions/permissions` (covered by the audit PAT's `Administration: read`): a fork with nil audits as `actions_enabled=unknown` and phase 3 still disables it, and `DisableActions` sends only `enabled=false` so the fork's allowed-actions policy is left alone.
- Ruleset compliance is a four-part check: name match, `non_fast_forward` rule, `allowed_merge_methods` on the `pull_request` rule equal to `DesiredAllowedMergeMethods()`, and `refs/heads/main` in the ref-name include list. A name-only match is not compliant (see `Ruleset.IsCompliant`). **`non_fast_forward` and `allowed_merge_methods` are not the same thing and the names actively mislead:** GitHub's `non_fast_forward` rule blocks *force pushes* and says nothing about how a pull request lands; restricting merges to merge commits — the actual no-fast-forward-*merge* policy — is `allowed_merge_methods`. `Ruleset.AllowedMergeMethods` is nil when the repo has no `pull_request` rule at all, which the audit reports as `rule_missing` rather than as an empty list.
- `RepositoryAdminActorType`/`RepositoryAdminActorID` (from `entities/compliance_policy.go`) stays in every ruleset's `BypassActors` so the owner can force-push when needed.
- **Phase 4 creates a ruleset only when there is none; a ruleset the audit found is updated by ID.** GitHub rejects a POST whose ruleset name is already taken with `422 Name must be unique`, so `applyRuleset` branches on `audit.Ruleset != nil` and calls `UpdateRuleset` for the drifted case. This matters every time the ruleset policy gains a rule: every already-hardened repo instantly becomes non-compliant *and* already owns the name, which is the exact combination that made an earlier `allowed_merge_methods` rollout fail on all 70 repos. Never "simplify" the branch back to a bare `CreateRuleset`.
- **An unprotected default branch is a normal state, not an audit failure.** `go-github` reports `404 Branch not protected` as its `ErrBranchNotProtected` sentinel — a plain `errors.New`, so it carries neither the status code nor the API's wording, and neither `isStatusCode(err, 404)` nor a `"Branch not protected"` string match will see it. `FindProtectionByBranch` tests `errors.Is(err, github.ErrBranchNotProtected)` first. Getting this wrong is quiet and expensive: the error becomes `AuditError`, and since phases 2-4 consult the audit rather than the live API, the repo is skipped by *every* phase while the report shows only `audit_error`.
- **The merge shape spans two layers, and neither half stands alone.** A semi-linear history is: rebase the PR onto its base (*Update with rebase*), then land it with a merge commit. GitHub has no single toggle for that, so the policy is assembled from four settings across the repo and its ruleset, and changing any one of them alone breaks it in a different direction.
  - Repo level (`DesiredRepoSettings()`): `AllowMergeCommit` on, `AllowSquashMerge` off, `AllowRebaseMerge` **on**, `AllowUpdateBranch` on.
  - Ruleset level (`DesiredAllowedMergeMethods()`): `allowed_merge_methods` = `["merge"]`.
  - `AllowRebaseMerge` is on for exactly one reason: it is the toggle that surfaces *Update with rebase*. It unavoidably also surfaces *Rebase and merge*, which fast-forwards without the merge commit — GitHub gates both on the same flag. Turning it off to hide that button also kills the update control, which is why the fast-forward is blocked by the ruleset instead. **A ruleset can only narrow what the repo already allows**, so removing `AllowRebaseMerge` while keeping the ruleset rule does not tighten anything; it just removes the button.
  - `AllowUpdateBranch` is "Always suggest updating pull request branches". Without it the *Update branch* control only appears when branch protection requires the branch be up to date before merging, which `DesiredBranchProtection()` does not require — so it is what makes the button reliably present.
  - **The ruleset's admin bypass (`RepositoryRole`/5, `always`) exempts repository admins from the merge-method rule too.** GitHub scopes a bypass actor to the whole ruleset, not to individual rules, so the force-push escape hatch and the merge-method restriction cannot be separated without splitting this into a second bypass-free ruleset. The restriction binds every collaborator and every bot; for the owner it is a guardrail, not a lock — the same posture as branch protection here, which runs with `EnforceAdmins` false. Splitting it is the fix if that ever stops being acceptable; weakening `DesiredAllowedMergeMethods()` is not.
- **The Sonar policy is scoped by rule key, never by file.** `entities.DesiredSonarIssueExclusions()` excludes `githubactions:S7637` on `**/*.y*ml` — the pattern covers composite actions (`action.yaml` at any depth), which the same `githubactions` language analyses and which carry the same first-party references. Every other rule keeps firing on those files, which is the entire reason this is an *issue exclusion* and not a `sonar.exclusions` entry: `S7634` (only pass required secrets) and `S7630` (script injection) are real findings the user wants reported. Widening this to `sonar.exclusions`, or deactivating the rule in a quality profile, silences them too. Third-party actions are still SHA-pinned; that policy is gated by the `pipelines` scheduled dependency job, not by S7637.
- **`entities.DesiredSonarTriagedRuleKeys()` is derived from the exclusion list, never written out by hand.** A rule excluded but not triaged leaves its already-recorded findings in place and the gate red until the project is analysed again.
- **`api/settings/set` replaces a property set wholesale**, so `ApplySonarPolicyCommand` reads the project's current exclusions and writes the union (`entities.MergeSonarIssueExclusions`). Writing only the policy pairs would silently drop anything configured by hand in the SonarQube Cloud UI, and rewriting an already-compliant project would log a change every single day.
- **The three Sonar sub-steps are attempted independently**, unlike phase 3 where a failure aborts the rest of the repo. They sit behind three different SonarQube Cloud project permissions — `Administer`, `Administer Issues`, `Administer Security Hotspots` — so one denial says nothing about the other two.
- `AuditResult.ComputeIssues` is the policy. Every command that decides whether to mutate consults the audit, not the live API — so phases 2/3/4 are re-reading a single audit list, not round-tripping to GitHub per repo.

Environment variables:

- `HARDEN_OWNER` (default: `rios0rios0`) — comma-separated GitHub owners/orgs to audit, walked in the order given. `parseOwners` in `cmd/harden-repos/main.go` trims whitespace, drops blanks, and collapses duplicates. A listing failure on any listed owner is fatal rather than a partial pass, and a fine-grained PAT is bound to a single resource owner — so **the workflows never pass more than one owner at a time**. Each fans out with `strategy.matrix.owner` and sets `HARDEN_OWNER` to that leg's owner alone. Passing the full comma-separated list is still correct locally, where one token can cover whatever you have access to.
- `GH_TOKEN` / `GITHUB_TOKEN` — bearer token for `github.com/google/go-github`. Each workflow resolves it per matrix leg via `secrets[matrix.owner.secret]`, from one PAT per owner: `PERSONAL_ACCESS_TOKEN`, `MEDHUB_ACCESS_TOKEN`, `PREFY_ACCESS_TOKEN`. The three GitHub workflows share the same three secrets, and so do `autobump-automation` and `autoupdate-automation`, so each owner needs exactly one PAT — scoped to the union of audit reads plus `Contents: write` and `Pull requests: write`. Every token's lifetime must be 366 days or less; `medhub-life` and `prefy` reject longer-lived fine-grained tokens with a 403.
- `SONAR_TOKEN` — SonarQube Cloud **user** token used by `--sonar-policy`. Not an analysis token: an analysis token can only submit reports. Absent, the read endpoints still answer for public projects (so `--sonar-policy --dry-run` needs no credential) and every mutation fails with the API's own denial message — which is not the same one everywhere. Uncredentialed, `api/settings/set` answers `404 Project doesn't exist` (SonarQube Cloud hides a project from a caller that cannot administer it) while `api/issues/bulk_change` and `api/hotspots/change_status` answer `401 Authentication is required`; an under-permissioned token gets `403 Insufficient privileges` instead.
- `SONAR_ORGANIZATION` (default: `rios0rios0`) — the single SonarQube Cloud organization `--sonar-policy` walks. Deliberately not `HARDEN_OWNER`: the other owners have no SonarQube Cloud organization.
- `SONAR_HOST_URL` (default: `https://sonarcloud.io`) — SonarQube Cloud base URL.
- `TMPDIR` — respected by `os.TempDir()` for the audit snapshot paths, so the binary runs on hosts where `/tmp` is not writable.

## Build / Test / Lint

```bash
make build                          # compile bin/harden-repos
make test                           # go test -race over cmd/ and internal/ via rios0rios0/pipelines
make lint                           # golangci-lint run ./...
make sast                           # run the full SAST suite from rios0rios0/pipelines
go test -run TestAuditRepositoriesCommand ./internal/domain/commands/
go test -count=1 ./cmd/refresh-docs/...  # the refresh end to end: local bare repos, a fake Claude CLI, an in-memory PR host
go test -count=1 ./test/scripts/...      # the release reconciliation's shell against local Git repositories (no test cache)
```

Test files use the `_test` package suffix (external tests), `t.Parallel()` on every top-level test function, BDD-style `// given / // when / // then` blocks, and the in-memory doubles in `test/domain/doubles/repositories/` rather than interface mocks. Unit tests carry no build tag, so a plain `go test ./...` runs every suite; `//go:build integration` is reserved for tests that need external infrastructure. `make test` covers only `cmd/` and `internal/`, so CI runs `test/scripts/` as `tests > test:scripts`, in the shared pipeline's tests stage (its `extra_test_command` input). The refresh's suites run real git and fake CLIs in child processes, which the test cache cannot see: pass `-count=1`. A fake CLI is written once in `TestMain`, since writing an executable while a parallel test forks makes running it fail with "text file busy".

## Conventions Specific to This Repo

- **YAML files use `.yaml`** (not `.yml`), with string values single-quoted except where interpolation requires double quotes.
- **Go conventions** follow `.claude/rules/golang.md` in the user's global rules: `snake_case` file names, one-letter receiver names (`c` for Command, `r` for Repository), manual constructor injection in each `cmd/<app>/container.go` (no Dig), Logrus for logging, testify for tests, no framework tags on entities.
- **Actions pins:** every step-level `actions/*` use is pinned to a full commit SHA with a trailing `# vX.Y.Z` comment (not a bare tag) — a security decision from `0.3.8`; do not "simplify" a SHA back to `@v6`. Keep every workflow on the same latest major (currently `actions/checkout` v6, `actions/upload-artifact` v7, `actions/setup-go` v6, `actions/setup-node` v6). When bumping, update the SHA *and* its comment across all four workflows (`repo-compliance-audit.yaml`, `config-and-docs-refresh.yaml`, `release-reconcile.yaml`, `sonar-analysis-policy.yaml`) in the same commit. The `@anthropic-ai/claude-code` npm package is the exception: `scripts/install-refresh-tools.sh` installs it from the open npm range `>=2.1.283` so the bundled prompt-audit command is available while newer releases remain eligible. Because that range is open, the `setup-node` major has to keep up with the CLI's `engines` floor (`>=22` as of `2.1.316`): npm only warns (`EBADENGINE`) on an older Node.js and installs the CLI anyway.
- **Go toolchain in workflows:** every `actions/setup-go` step uses `go-version-file: 'go.mod'` — never a hardcoded `go-version`. `setup-go` exports `GOTOOLCHAIN=local`, so a loose spec like `'1.26'` silently resolves to whatever patch release the runner has cached (e.g. 1.26.4) and then hard-fails every `go run` the moment `go.mod` requires a newer patch (`go 1.26.5`). Bumping `go.mod` is therefore enough; the workflows follow automatically, and so does the Azure Pipelines template, which reads the `go` directive before `GoTool@0`.
- **Changelog discipline:** every change writes its own fragment under `.changes/unreleased/` with `chlog new --kind <Kind> --body '...'`, in the same commit. `CHANGELOG.md` is generated from the fragments at release time and is never edited by hand. Keep a Changelog kinds, simple past tense, backticks around code identifiers.
- **Commits:** `type(SCOPE): message` in simple past tense, no trailing period. See `.claude/rules/git-flow.md` in the user's global rules.
- **Ruleset / branch-protection changes are load-bearing.** Every `rios0rios0` repo inherits the same policy; a change here propagates to all of them on the next audit run.

If the repository you are working in uses chlog (a `.chlog.yaml` or `.chlog.yml`
