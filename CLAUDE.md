# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Repository Is

This repo houses **scheduled, cross-repo maintenance workflows** that run from a central location and act on every repository of every owner listed in `HARDEN_OWNER` (currently `rios0rios0`, `medhub-life`, and `prefy`), plus the Go CLI they drive.

**One job per owner is the workflow baseline.** Because a fine-grained PAT is bound to a single resource owner, every scheduled workflow fans out with `strategy.matrix.owner` (`fail-fast: false`) and gives each leg its own owner and its own token. `config-and-docs-refresh.yaml` additionally enumerates each owner separately and keeps going past an unreachable one, then fails the run in its terminal `verify` job — so a skipped owner is loud instead of silently shrinking the fleet.

**Multi-owner is the CLI's baseline, not a special case.** `HARDEN_OWNER` is a comma-separated list; every phase loops over it. Two consequences are load-bearing: a repository is identified by its `owner/name` slug (`entities.Repository.QualifiedName()`) because bare names collide across owners — `medhub-life/frontend` and `prefy/frontend` both exist today — and the mutating phases receive per-owner command inputs, which is why `executeAuditPerOwner` keeps the audits grouped instead of returning one flat slice. Anything that maps, keys, or reports repositories must use the qualified name; keying on the bare name silently attributes one owner's drift to another's repo.

1. **`.github/workflows/repo-compliance-audit.yaml`** — daily (06:00 UTC) audit that runs `go run ./cmd/harden-repos --phase 1 --fail-on-noncompliant` against every repo of every configured owner. Fails if any repo drifts from the compliance policy. Uploads `/tmp/gh_hardening_audit_before.json` as an artifact.

2. **`.github/workflows/config-and-docs-refresh.yaml`** — weekly (Mondays 07:00 UTC) **batched-matrix** workflow. Named for the broader scope (configuration + documentation) so future targets — diagrams, additional config files — can be added without renaming; today the in-scope set is the AI-assistant guidance files plus the tailored GitHub Copilot code-review skill at `.github/skills/code-review/SKILL.md`. The `discover` job calls `go run ./cmd/harden-repos --list-json` to enumerate non-fork non-archived repos, then chunks the sorted list into fixed-size batches (default `batch_size: 10`, overridable per-run via `workflow_dispatch`). The `refresh` job is a matrix with one leg per batch (`max_parallel: 2` by default); each leg installs `@anthropic-ai/claude-code` via `npm`, self-checks-out this repo to load `scripts/refresh_config_and_docs_prompt.md`, and then loops through its batch internally — cloning each target repo into a scratch directory, invoking the Claude Code CLI with a tool allowlist locked to `Read,Grep,Glob,Edit(/CLAUDE.md),Edit(/.github/copilot-instructions.md),Edit(/.github/skills/code-review/SKILL.md)` plus one changelog grant chosen per repo (see below), detecting drift, and opening a PR. **Every grant is an `Edit(...)` rule, never `Write(...)`:** the CLI matches file permissions on `Edit` rules alone — an `Edit` grant covers every file-editing tool including `Write` (so creating a file the repo lacked is already allowed), while a `Write(...)` rule is inert and only earns `Permission allow rule (--allowed-tools): Write(...) is not matched by file permission checks` on stderr. The four `Write(...)` entries this allowlist used to carry never granted anything. The `claude` invocation is fed `</dev/null` — load-bearing because otherwise `claude -p` inherits the outer `while read` loop's stdin (the `jq` pipe) and silently drains the rest of the batch after the first repo. It is also wrapped in `set +e` / `set -e`, which is load-bearing for the same reason: the step runs under `set -euo pipefail`, so with `pipefail` the `claude … | tee` pipeline's status *is* `claude`'s exit code and a non-zero exit would abort the entire leg on the spot — stranding every repo after the failing one and skipping the `==== Batch summary ====` entirely. Suspending `errexit` around the pipeline keeps a `claude` failure local to the repo that caused it. **Every failure mode inside the per-repo loop must stay non-fatal to the batch; a bare, unguarded command in the loop body is a bug.** `claude`'s output is tee'd to `${WORK_DIR}/.claude.log` so `PIPESTATUS[0]` can be classified against it: `monthly usage limit` is org-wide, so it sets `quota_hit=1` and short-circuits the rest of the batch (each surviving repo is reported on a `quota_skipped` line instead of burning ~3min/repo against an exhausted quota); a safeguard refusal (`safeguards flagged` / `cyber-use-case`, which Claude raises on some security-topic repos) is deterministic for that one repo and says nothing about the others, so it is recorded as `claude-safeguard:` and the loop simply moves to the next repo; anything else (transient API error, max-turns abort) is recorded as `claude:` and likewise skipped. Drift detection uses `git add -N` (intent-to-add) followed by `git diff -w --quiet` so modified and newly-created in-scope files both count; whitespace-only diffs are ignored. The in-scope set lives in exactly three places that must move together: the `IN_SCOPE` array at the top of the step, the `--allowedTools` string on the same step, and the file list in `scripts/refresh_config_and_docs_prompt.md`. `drift_paths` and the activity gate's `:(exclude)` arguments are both *derived* from `IN_SCOPE` rather than repeating it, which is what keeps the count at three. Adding a path to `drift_paths` without the matching `Edit` grant produces a permanently no-drift target, because Claude is denied the tool it would need to change it. **The changelog target is chosen per repo, and the allowlist — not the prompt — is what enforces the choice.** `changelog_mode` is `chlog` when the clone has `.chlog.yaml`, `.chlog.yml`, or a `.changes/unreleased/` directory — the predicate copied verbatim from the `pipelines` basic-checks gate, which mirrors AutoBump's `DetectChlog`, so the three cannot disagree (grant: `Edit(/.changes/unreleased/**)`), `changelog` when it only has a `CHANGELOG.md` (grant: `Edit(/CHANGELOG.md)`), and `none` otherwise (no grant); the matching half of the prompt's `## Recording the change` section is appended to the per-repo prompt as `## Changelog convention for this repository`. In a chlog repo `CHANGELOG.md` is *generated* from the fragments, so an entry written into it by hand is discarded by the next `chlog batch` and puts the rebase conflicts the fragments exist to prevent back on that one file — which is exactly what the 2026-08-31 run did to 46 repositories, because the prompt told Claude to edit the CHANGELOG and the grant let it. Granting only one convention's tool makes the other impossible rather than merely discouraged; a post-refresh guard additionally reverts any `CHANGELOG.md` or existing-fragment change in chlog mode and rejects the repo with a `fragment:` failure if a new fragment lacks a `kind:`/`body:`/`time:` line. Both restores are flagged rather than bare — a bare command in an `if` *body* is subject to `errexit`, so a failed restore would abort the leg mid-loop; it is recorded as `changelog-guard:` and skips only that repo, because letting it through would open a PR carrying the very edit the guard exists to prevent. Both changelog targets are staged alongside the in-scope files (so the entry lands in the same PR) but neither is part of the drift gate — a stray changelog-only edit cannot open a spurious PR. **A repo whose code has not changed is not refreshed at all.** After the clone and before the `claude` call, the leg reads `git log -1 --first-parent -- . :(exclude)<every path this job writes>` and skips the repo when that predates `stale_after_days` (default 8), reporting it on the `unchanged` summary line. Three details are load-bearing: the excludes are derived from `IN_SCOPE` so the job's own output never counts as activity — the default branch's HEAD date is self-defeating here, since merging a refresh PR makes every repo the job touched look busy the next week; `--first-parent` is required because pathspec history simplification otherwise follows whichever parent a merge is TREESAME to, reporting a long-lived branch's authoring date instead of its merge date and skipping that repo forever; and a repo carrying **none** of the in-scope files is never skipped, because "quiet" only means "up to date" once the job has produced something there. `stale_after_days` is passed to the step raw and defaulted in bash — `${{ inputs.x || '8' }}` would break the documented `0` escape hatch, since GitHub's `||` treats the numeric `0` as falsy. Use `stale_after_days: 0` to force a full-fleet pass, which is what a newly added refresh target needs. Branch name is stable (`chore/config-and-docs-refresh`) and force-pushed so repeated runs update a single open PR. Each leg prints a `==== Batch summary ====` footer listing `processed / unchanged / no_drift / prs_created / prs_updated / quota_skipped / failed` (the last one per line, since each entry is a `<reason>: <owner>/<repo>` pair) and exits non-zero only if at least one repo failed. `quota_skipped` does not by itself fail the leg, but every reason recorded in `failed` — `clone:`, `checkout:`, `branch:`, `commit:`, `push:`, `pr-list:`, `pr-create:`, `claude:`, `claude-quota:`, `claude-safeguard:`, `changelog-guard:`, `fragment:` — does. A safeguard refusal is therefore a permanently red leg for as long as that repo trips it: the intended resolutions are to fix the trigger, exclude the repo, or obtain an exemption — not to downgrade it to a silent skip, which would let that repo's docs rot unnoticed.

3. **`.github/workflows/release-reconcile.yaml`** — weekly (Mondays 08:00 UTC) safety net for the "bumped but never released" failure mode: a bump PR merges but that repo's `main` run fails the pipelines quality gate, so `delivery-release` never runs and no tag/release is cut even though `CHANGELOG.md` already carries the version. The job enumerates repos via `go run ./cmd/harden-repos --list-json`, clones `pipelines` for the single-sourced detector `global/scripts/shared/reconcile-releases.sh`, then runs `scripts/reconcile-repos.sh` — which blobless-clones each repo, diffs its released changelog versions against its tags, and (re-)pushes any missing tag at its bump commit. The tag push re-triggers the `pipelines` tag-push delivery path (the gate jobs skip on tags), which re-cuts the release. Pushes use that owner's PAT — a `GITHUB_TOKEN`-pushed tag would not start the delivery workflow. `workflow_dispatch` exposes `repo` (single-repo), `dry_run` (detect + report only), and `fail_on_gap` (exit non-zero on an unrecoverable gap) inputs; results are written to `$GITHUB_STEP_SUMMARY`. Detection is single-sourced in `pipelines` (and tested there), so this repo owns only the org-wide orchestration.

4. **`cmd/harden-repos/`** — the Go CLI that implements the compliance policy. Understanding its architecture is required before editing.

## The `harden-repos` CLI

Clean Architecture split:

- **`internal/domain/entities/`** — framework-agnostic data types: `Repository`, `SecuritySettings`, `BranchProtection`, `Ruleset`, `AuditResult`. `compliance_policy.go` exposes the policy every other package references: `DesiredRepoSettings()` and `DesiredWikiAllowlist()` are functions (returning fresh values so the policy stays immutable at call sites); `DesiredReviewCount`, `DesiredForkActionsEnabled`, `DesiredRulesetName`, `DesiredDefaultBranch`, and `RepositoryAdminActorType`/`ID` remain constants. `AuditResult.ComputeIssues()` is the single source of truth for policy compliance and encodes every carve-out (forks skip Dependabot + secret scanning and must instead keep GitHub Actions disabled — `DesiredForkActionsEnabled`, reported as `actions_enabled`, never checked on a non-fork — private repos skip secret scanning + branch protection + rulesets, `DesiredWikiAllowlist()` repos keep `has_wiki=true`, `AllowAutoMerge=true` is skipped on private repos because GitHub Free silently ignores the PATCH).
- **`internal/domain/repositories/`** — three ports: `Repository`, `SecuritySettingsRepository`, `BranchProtectionsRepository`. Each is a small interface with the methods the commands actually need. The domain layer never imports `github.com/google/go-github`. `BranchProtectionsRepository.FindRulesetByName` returns the sentinel `repositories.ErrRulesetNotFound` when no ruleset is configured; callers treat it as "no ruleset" rather than propagating it as an error.
- **`internal/domain/commands/`** — one command per phase plus `--list-json`: `AuditRepositoriesCommand`, `ApplyRepositorySettingsCommand`, `ApplySecuritySettingsCommand`, `ApplyBranchProtectionCommand`, `ListTargetRepositoriesCommand`, `ReportComplianceChangesCommand`. Every command exposes a listeners struct (`OnSuccess`, `OnError`, `OnChange`, etc.) so the CLI layer (which plays the controller role) maps outcomes to stdout and exit codes.
- **`internal/infrastructure/repositories/`** — `GoGithub…Repository` adapters that implement the ports by calling `github.com/google/go-github/v75`. Each also handles the HTTP-status idioms the Python original encoded: 204 vs 404 for vulnerability alerts, 403/404 for branch protection unavailability, rate limits, etc.
- **`cmd/harden-repos/main.go`** — parses flags, dispatches to commands with listeners that print via Logrus and set exit codes.

Key invariants to preserve when editing:

- `Repository.FindAllByOwner` branches on whether the owner equals the authenticated login (then `/user/repos` retains private visibility) and on `OwnerKind` (`User` vs `Organization`). Keep all three paths in sync.
- `SecuritySettingsRepository.FindByRepositoryName` returns `DependabotAlerts *bool` — nil means "unknown" (API failure), pointer-to-false means "disabled". `AuditResult.ComputeIssues` distinguishes the two; don't collapse them. `ActionsEnabled *bool` carries the same tri-state for the repository-level GitHub Actions switch, read from `GET /repos/{owner}/{repo}/actions/permissions` (covered by the audit PAT's `Administration: read`): a fork with nil audits as `actions_enabled=unknown` and phase 3 still disables it, and `DisableActions` sends only `enabled=false` so the fork's allowed-actions policy is left alone.
- Ruleset compliance is a four-part check: name match, `non_fast_forward` rule, `allowed_merge_methods` on the `pull_request` rule equal to `DesiredAllowedMergeMethods()`, and `refs/heads/main` in the ref-name include list. A name-only match is not compliant (see `Ruleset.IsCompliant`). **`non_fast_forward` and `allowed_merge_methods` are not the same thing and the names actively mislead:** GitHub's `non_fast_forward` rule blocks *force pushes* and says nothing about how a pull request lands; restricting merges to merge commits — the actual no-fast-forward-*merge* policy — is `allowed_merge_methods`. `Ruleset.AllowedMergeMethods` is nil when the repo has no `pull_request` rule at all, which the audit reports as `rule_missing` rather than as an empty list.
- `RepositoryAdminActorType`/`RepositoryAdminActorID` (from `entities/compliance_policy.go`) stays in every ruleset's `BypassActors` so the owner can force-push when needed.
- **Phase 4 creates a ruleset only when there is none; a ruleset the audit found is updated by ID.** GitHub rejects a POST whose ruleset name is already taken with `422 Name must be unique`, so `applyRuleset` branches on `audit.Ruleset != nil` and calls `UpdateRuleset` for the drifted case. This matters every time the ruleset policy gains a rule: every already-hardened repo instantly becomes non-compliant *and* already owns the name, which is the exact combination that made an earlier `allowed_merge_methods` rollout fail on all 70 repos. Never "simplify" the branch back to a bare `CreateRuleset`.
- **An unprotected default branch is a normal state, not an audit failure.** `go-github` reports `404 Branch not protected` as its `ErrBranchNotProtected` sentinel — a plain `errors.New`, so it carries neither the status code nor the API's wording, and neither `isStatusCode(err, 404)` nor a `"Branch not protected"` string match will see it. `FindProtectionByBranch` tests `errors.Is(err, github.ErrBranchNotProtected)` first. Getting this wrong is quiet and expensive: the error becomes `AuditError`, and since phases 2-4 consult the audit rather than the live API, the repo is skipped by *every* phase while the report shows only `audit_error`.
- **The merge shape spans two layers, and neither half stands alone.** A semi-linear history is: rebase the PR onto its base (*Update with rebase*), then land it with a merge commit. GitHub has no single toggle for that, so the policy is assembled from four settings across the repo and its ruleset, and changing any one of them alone breaks it in a different direction.
  - Repo level (`DesiredRepoSettings()`): `AllowMergeCommit` on, `AllowSquashMerge` off, `AllowRebaseMerge` **on**, `AllowUpdateBranch` on.
  - Ruleset level (`DesiredAllowedMergeMethods()`): `allowed_merge_methods` = `["merge"]`.
  - `AllowRebaseMerge` is on for exactly one reason: it is the toggle that surfaces *Update with rebase*. It unavoidably also surfaces *Rebase and merge*, which fast-forwards without the merge commit — GitHub gates both on the same flag. Turning it off to hide that button also kills the update control, which is why the fast-forward is blocked by the ruleset instead. **A ruleset can only narrow what the repo already allows**, so removing `AllowRebaseMerge` while keeping the ruleset rule does not tighten anything; it just removes the button.
  - `AllowUpdateBranch` is "Always suggest updating pull request branches". Without it the *Update branch* control only appears when branch protection requires the branch be up to date before merging, which `DesiredBranchProtection()` does not require — so it is what makes the button reliably present.
  - **The ruleset's admin bypass (`RepositoryRole`/5, `always`) exempts repository admins from the merge-method rule too.** GitHub scopes a bypass actor to the whole ruleset, not to individual rules, so the force-push escape hatch and the merge-method restriction cannot be separated without splitting this into a second bypass-free ruleset. The restriction binds every collaborator and every bot; for the owner it is a guardrail, not a lock — the same posture as branch protection here, which runs with `EnforceAdmins` false. Splitting it is the fix if that ever stops being acceptable; weakening `DesiredAllowedMergeMethods()` is not.
- `AuditResult.ComputeIssues` is the policy. Every command that decides whether to mutate consults the audit, not the live API — so phases 2/3/4 are re-reading a single audit list, not round-tripping to GitHub per repo.

Environment variables:

- `HARDEN_OWNER` (default: `rios0rios0`) — comma-separated GitHub owners/orgs to audit, walked in the order given. `parseOwners` in `cmd/harden-repos/main.go` trims whitespace, drops blanks, and collapses duplicates. A listing failure on any listed owner is fatal rather than a partial pass, and a fine-grained PAT is bound to a single resource owner — so **the workflows never pass more than one owner at a time**. Each fans out with `strategy.matrix.owner` and sets `HARDEN_OWNER` to that leg's owner alone. Passing the full comma-separated list is still correct locally, where one token can cover whatever you have access to.
- `GH_TOKEN` / `GITHUB_TOKEN` — bearer token for `github.com/google/go-github`. Each workflow resolves it per matrix leg via `secrets[matrix.owner.secret]`, from one PAT per owner: `PERSONAL_ACCESS_TOKEN`, `MEDHUB_ACCESS_TOKEN`, `PREFY_ACCESS_TOKEN`. All three workflows share the same three secrets, and so do `autobump-automation` and `autoupdate-automation`, so each owner needs exactly one PAT — scoped to the union of audit reads plus `Contents: write` and `Pull requests: write`. Every token's lifetime must be 366 days or less; `medhub-life` and `prefy` reject longer-lived fine-grained tokens with a 403.
- `TMPDIR` — respected by `os.TempDir()` for the audit snapshot paths, so the binary runs on hosts where `/tmp` is not writable.

## Conventions Specific to This Repo

- **YAML files use `.yaml`** (not `.yml`), with string values single-quoted except where interpolation requires double quotes.
- **Go conventions** follow `.claude/rules/golang.md` in the user's global rules: `snake_case` file names, one-letter receiver names (`c` for Command, `r` for Repository), Uber Dig for DI, Logrus for logging, testify for tests, no framework tags on entities.
- **Actions pins:** every step-level `actions/*` use is pinned to a full commit SHA with a trailing `# vX.Y.Z` comment (not a bare tag) — a security decision from `0.3.8`; do not "simplify" a SHA back to `@v6`. Keep every workflow on the same latest major (currently `actions/checkout` v6, `actions/upload-artifact` v7, `actions/setup-go` v6, `actions/setup-node` v6). When bumping, update the SHA *and* its comment across all three workflows (`repo-compliance-audit.yaml`, `config-and-docs-refresh.yaml`, `release-reconcile.yaml`) in the same commit. The `@anthropic-ai/claude-code` npm package is the exception: pinned implicitly to `latest` via `npm install -g`; rely on the CLI's own version skew tolerance rather than pinning a specific version.
- **Go toolchain in workflows:** every `actions/setup-go` step uses `go-version-file: 'go.mod'` — never a hardcoded `go-version`. `setup-go` exports `GOTOOLCHAIN=local`, so a loose spec like `'1.26'` silently resolves to whatever patch release the runner has cached (e.g. 1.26.4) and then hard-fails every `go run` the moment `go.mod` requires a newer patch (`go 1.26.5`). Bumping `go.mod` is therefore enough; the workflows follow automatically.
- **Changelog discipline:** every change writes its own fragment under `.changes/unreleased/` with `chlog new --kind <Kind> --body "..."`, in the same commit. `CHANGELOG.md` is generated from the fragments at release time and is never edited by hand. Keep a Changelog kinds, simple past tense, backticks around code identifiers.
- **Commits:** `type(SCOPE): message` in simple past tense, no trailing period. See `.claude/rules/git-flow.md` in the user's global rules.
- **Ruleset / branch-protection changes are load-bearing.** Every `rios0rios0` repo inherits the same policy; a change here propagates to all of them on the next audit run.

## Changelog (chlog) — MANDATORY

If the repository you are working in uses chlog (a `.chlog.yaml` or `.chlog.yml`
config file, or a `.changes/` directory, exists at the project root), the
following is binding and ALWAYS applies: whenever you make ANY change, you MUST
create a changelog fragment as part of the same change — automatically, without
being asked, before committing.

- Do NOT edit CHANGELOG.md directly; it is generated from fragments.
- Create the fragment with:
  `chlog new --kind <Kind> --body "<imperative description>"`
- Valid kinds: Added, Changed, Deprecated, Removed, Fixed, Security
- Choose the kind that best matches the change (e.g., new feature → Added,
  bug fix → Fixed, behavior change → Changed, removal → Removed, security fix → Security).
- If the change is backward-INCOMPATIBLE with the public API (a breaking
  change), you MUST add the `--breaking` flag:
  `chlog new --kind <Kind> --breaking --body "<description>"`.
  This is the ONLY thing that triggers a major version bump — the kind alone
  never does (per SemVer, major = incompatible change). When unsure whether a
  change breaks compatibility, ask the user instead of guessing.
- Fragments are YAML files in `.changes/unreleased/`; stage them with your commit.
- `chlog check` fails the build when a fragment is missing — never skip it.
